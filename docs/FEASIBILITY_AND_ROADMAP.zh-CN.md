# OpenBrowser 二次开发可行性与路线图

审查基线：`1129Aliasgar/OpenBrowser`，提交 `2f090f0954435efb07ee35f95e04576b7c6d65fa`。

## 结论

项目适合作为本地 AI 编程 Agent 的原型底座，但不应直接把现状包装成成熟、安全的通用 Agent。它已经具备浏览器桥接、项目摘要、结构化文件操作、Diff 预览和人工确认，因此最经济的路线是保留这些模块，在外围补上后端抽象、事务、验证和安全策略，而不是重写 CLI 或浏览器扩展。

技术可行性：高。产品可行性：中高。合规可行性：取决于每个模型服务的条款和用户账户权限，应提供官方 API、本地模型或用户明确允许的浏览器连接方式，不承诺“无限免费”，不规避配额、验证码、付费墙或风控。

## 许可结论

仓库采用 MIT License，可以使用、复制、修改、合并、发布、分发、再许可和销售衍生版本。二次发布时必须保留原始版权声明和 MIT 许可文本。可以更换项目名、商标、界面和新增版权声明，但不能删除原作者的版权与许可，也不应暗示原作者为新项目背书。

建议做法：

- 保留根目录 `LICENSE` 原文，并在其后追加新项目贡献者的版权声明。
- 在 README 的 Credits/Upstream 中标明基于 OpenBrowser 及对应提交。
- 对新写代码使用相同 MIT 许可，除非未来引入的依赖要求兼容处理。
- 发布前生成第三方依赖清单，并核对浏览器扩展商店政策及各模型服务条款。

## 现有模块审查

| 模块 | 现状 | 复用判断 | 主要问题 |
| --- | --- | --- | --- |
| `src/index.ts` | CLI、ask/agent 主循环、最多三次重试 | 保留并逐步拆分 | 编排逻辑集中，后期需抽为工作流状态机 |
| `src/context/` | 项目扫描、`@file`/`@folder`、大小上限 | 保留 | 只有文件列表和显式附件，缺少符号/依赖图、秘密扫描和 token 预算器 |
| `src/protocol/`、`src/parser/` | Zod 操作协议、混合文本解析 | 保留协议，逐步简化解析 | 输出格式复杂；后端支持结构化输出后应减少脆弱的 Markdown 解析 |
| `src/operations/` | Diff、文件执行、命令执行 | 保留 Diff，强化执行边界 | 上游版本无事务，命令不可回滚，需防符号链接穿越 |
| `src/server/` | Fastify、SSE、会话队列 | 保留 | 内存会话、单进程；原 CORS 过宽，配对认证仍需加强 |
| `browser-extension/` | 多站点注入、抓取/接口捕获 | 作为一种后端保留 | DOM/API 易变；服务条款差异；权限面较宽；不应成为唯一后端 |
| `src/memory/` | `.openbrowser` 中的摘要和历史 | 保留格式，升级语义 | 原历史只记摘要，不足以恢复或审计完整变更 |

## 最小侵入式架构

```text
CLI / future UI
      |
Agent workflow (bounded retries, approvals)
      |
ModelBackend interface
      +-- BrowserBackend (current single backend)
      +-- Official API backend (later)
      +-- Local model backend (later)
      |
Structured operations -> Diff review -> Transactional apply
                                      -> sandbox-copy verification
                                      -> commit or rollback
                                      -> failure feedback to same conversation
```

边界原则：模型只提出变更，宿主程序负责验证、授权和执行；模型输出不是可信输入。第一阶段只允许文件和文件夹操作，模型提出的 `RUN_COMMAND` 默认拒绝。依赖安装、迁移、Docker 和部署仍由用户明确执行。

## 已完成的首批开发工作

1. 新增 `ModelBackend` 接口，并将现有浏览器桥接包装为单一 `BrowserBackend`。这保持当前行为，同时为官方 API、本地模型和以后路由预留稳定入口。
2. 文件操作改为事务式：执行前快照所有目标和缺失父目录；任何写入、验证或回调失败时恢复原文件并删除本次创建的路径。
3. 拒绝符号链接路径、目录冒充文件、覆盖式 `CREATE_FILE`、覆盖式重命名等危险边界。
4. 默认禁用模型提出的 `RUN_COMMAND`，并同步修改系统提示词，避免不可回滚的命令混入文件事务。
5. 新增临时工作副本验证器：按固定顺序发现并执行 `typecheck`、`test`、`lint`、`build`；复制时排除 `.git`、`.openbrowser`、构建产物和依赖目录；只将依赖目录链接到副本。
6. 验证失败会触发文件回滚，错误文本进入现有最多三次的同会话重试链路。每次新方案仍需用户重新审核 Diff。
7. 历史记录增加 `applied`、`rolled_back`、`failed` 结果和验证详情。
8. 收紧本地桥接服务的 CORS：只允许无 Origin 的本地客户端和 Chrome 扩展 Origin，拒绝普通网页跨站访问。
9. 删除包对自身的 `link:` 依赖及对应锁文件覆盖，修复安装环路。

验证结果：TypeScript 类型检查通过；3 个测试文件、8 个测试通过，覆盖事务回滚、命令拒绝、覆盖保护、沙箱副本写隔离和 Origin 策略。

## 阶段计划

### 阶段 1：单模型完整闭环（当前主线）

目标是先把一条链路做可靠，不做多模型表面功能。

- 增加显式配置文件：后端、上下文预算、验证脚本白名单、超时和最大重试次数。
- 将 Agent 主循环从 `src/index.ts` 抽为可测试的状态机。
- 把事务快照持久化为内容寻址的变更集，增加 `history list/show/rollback` CLI。
- 为验证器增加输出大小限制、进程树终止和用户可选的容器执行器。
- 增加端到端测试：模拟后端返回补丁、审核、验证失败、反馈、第二次成功及回滚。
- 增加秘密文件忽略规则，并在发送上下文前显示将被上传到模型服务的文件清单。

完成门槛：同一任务能在不执行模型命令的前提下完成“读取 → 提案 → Diff → 应用 → 验证 → 成功/回滚 → 有限重试”；每一步有可审计记录。

### 阶段 2：ZIP 导入与安全隔离

- ZIP 先解压到新建临时目录，拒绝绝对路径、`..`、符号链接、设备文件和解压炸弹。
- 设置文件数、单文件大小、总解压大小和嵌套层级限制。
- 引入容器或受限进程执行器；默认断网、只挂载临时工作副本、限制 CPU/内存/时间。
- 命令能力改为策略对象：解析后的可执行文件和参数、逐条审批、网络和文件系统能力声明。

### 阶段 3：多模型路由

- 在单后端接口稳定后加入 capability 描述：上下文长度、结构化输出、工具调用、成本/限额、隐私等级。
- 路由只基于用户允许的后端和可用额度；失败时明确降级，不静默切换到隐私边界不同的服务。
- 免费后端仅指服务商公开允许的免费方案或本地模型。不得轮换账户、伪造客户端、绕过限流或自动处理验证码。

### 阶段 4：子 Agent

- 子 Agent 先做只读角色（检索、规划、测试分析），每个角色有独立上下文和预算。
- 只有主 Agent 能提交变更集；子 Agent 不能直接写工作区或执行命令。
- 合并以显式证据和冲突检测为准，不以多数投票替代验证。

### 阶段 5：可视化界面

- UI 只调用已有工作流 API，不复制执行逻辑。
- 第一屏优先展示上下文清单、Diff、验证日志、风险提示和回滚按钮。
- 最后再增加模型路由图、子 Agent 时间线和成本/额度面板。

## 当前限制与下一批任务

- 临时工作副本隔离的是项目写入，不是强安全沙箱；测试进程仍可能访问操作系统和网络。强隔离属于阶段 2。
- 浏览器后端依赖第三方网页结构和账户条款，稳定性低于官方 API 或本地模型。
- 浏览器扩展尚未实现一次性配对密钥；目前 Origin 白名单只是第一道防线。
- 回滚覆盖宿主执行的结构化文件操作，不承诺恢复外部进程、数据库、网络服务或测试脚本在项目外产生的副作用。
- 上下文摘要尚未做语义检索和秘密扫描，因此默认应从小范围 `@file`/`@folder` 开始。

建议下一批按顺序实现：持久化变更集与 `rollback` 命令、桥接配对令牌、配置与验证白名单、端到端假后端测试、容器执行器原型。完成这些后，再开始多模型路由。
